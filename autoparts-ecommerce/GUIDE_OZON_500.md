## СУТЬ ЗАДАЧИ

Ozon периодически открывает нам дополнительные слоты под товары (партиями по 500).
Нужно из свежего каталога Микадо отобрать 500 позиций, которых у нас ещё нет на Ozon,
с закупкой не дешевле 300 ₽, максимизирующих оборот и прибыль, с текстовым обоснованием
по каждой позиции — и свести в Excel.

Это повторяющаяся задача: при каждом новом транше слотов (Озон-1000, Озон-1500 и т.д.)
запускать тот же пайплайн заново со свежими данными.

## ИСТОЧНИКИ ДАННЫХ (без платных API)

1. **Ozon Seller API** — `/v3/product/list` (текущий каталог) + `/v1/analytics/data`
   (оборот/продажи за 90 дней). Используется как МЯГКИЙ бонус (до +50%), не доминирующий —
   у нас пока узкий ассортимент на Ozon (~7-10 категорий), статистика скудная.
2. **Прайс Микадо** — свежая выгрузка напрямую по ссылке (без логина):
   `https://mikado-parts.ru/api/Price/GetPriceExcel?StockId=34&Key=YOUR_MIKADO_PRICE_KEY`
   Кэшируется на 12 часов (`fetch_mikado_fresh()` в `ozon_top500_selector.py`).
3. **Публичная выдача Ozon** (`ozon_public_demand_scan.py`) — ГЛАВНЫЙ сигнал спроса.
   Playwright открывает поиск по ozon.ru для каждой товарной категории, собирает у
   верхних ~16 карточек число отзывов (= прокси накопленных продаж, т.к. отзывы
   начисляются только подтверждённым покупателям) и медианную цену.
4. **pricing_engine.py / price_recalc.py** — расчёт цены продажи и маржи ⚠️ **важно**:
   план **«Оптимум»** (`get_optimal_markup()`), наценка по тиерам закупки:
   | Закупка | Наценка |
   |---|---|
   | < 500 ₽ | 30% |
   | < 1200 ₽ | 25% |
   | < 2500 ₽ | 22% |
   | < 3500 ₽ | 20% |
   | ≥ 3500 ₽ | 17% |

   Логистика FBS по умолчанию 115 ₽ (нет габаритов в сыром прайсе Микадо).
5. **CAR_FLEET / PART_FREQ** — популярность моделей авто в автопарке РФ (Автостат) и
   частота замены детали — перенесены из методологии `wb_top500_combined.py`.

**MPStats НЕ используется** — пользователь явно отказался (подключён в проекте только
под Wildberries, для Ozon это был бы нерелевантный прокси).

## ФОРМУЛА СКОРИНГА

```
score = ext_demand × internal_bonus × consumable_mult × fleet_mult × margin_score × profit_component
```

- **ext_demand** = `log(1 + среднее число отзывов по категории)` — главный, объективный сигнал
- **internal_bonus** = `1 + min(log(1+продажи_категории)×0.15 + log(1+продажи_бренда)×0.15, 0.5)` —
  мягкая надбавка по нашей факт. статистике Ozon, максимум +50%
- **consumable_mult** — буст до ×1.5 для расходников короткого цикла (масляные/воздушные
  фильтры, свечи, колодки)
- **fleet_mult** — буст до ×1.35 для деталей к самым массовым моделям (Kia Rio, Lada Granta...)
- **margin_score** = `min(маржа/25%, 1.2)`
- **profit_component** = `log(1 + прибыль руб/шт.)`

## ФИЛЬТРЫ ОТБОРА

- Закупка ≥ 300 ₽ (задаётся `MIN_PURCHASE`, менять под конкретный транш)
- Маржа ≥ 8% (`MIN_MARGIN_PCT`)
- Остаток на складе Микадо > 0
- Уже загружен на Ozon → исключается (сверка `код Микадо + "-con"` против активных офферов)
- **Жидкости (моторное масло, антифриз/тосол) исключены** — по прямому указанию
  пользователя, см. `is_excluded_liquid()`. Фильтры/насосы со словом "масл" в названии
  НЕ исключаются (это не сама жидкость).
- Макс. **25 позиций на бренд** (`MAX_PER_BRAND`)
- Макс. **30 позиций на категорию** (`MAX_PER_CATEGORY`)

## ВАЖНЫЕ ГРАБЛИ (уже наступили, не повторять)

1. **Классификатор категорий (`CATEGORY_KW`) должен быть полным.** Первая версия
   оставляла 42% подходящих товаров в бакете "Прочее" (не участвовали в скоринге вообще)
   из-за неполного списка ключевых слов. Расширили до ~60 категорий, снизили до ~16-20%.
   При новом транше — проверять долю "Прочее" (`log.info` в скрипте это печатает) и
   при необходимости добавлять новые ключевые слова в `CATEGORY_KW`.
2. **Лимит на категорию (`MAX_PER_CATEGORY`) обязателен.** Без него отбор механически
   смещается в категории, где у Микадо просто больше SKU (колодки, амортизаторы) —
   это артефакт ассортимента поставщика, а не реальный спрос. С лимитом получается
   честное распределение по 25-35 категориям.
3. **Порядок слов в ключевых словах имеет значение** (это substring-matching, не
   AND-логика по стемам) — "цилиндр рабочий" ≠ "рабочий цилиндр". Проверять оба порядка
   для новых ключевых слов.
4. **Ozon headless-скрапинг не работает** — только видимый браузер.
5. **Микадо иногда таймаутит** при повторной загрузке прайса — есть retry + 12-часовой
   кэш-fallback в `fetch_mikado_fresh()`, ничего чинить не надо, просто перезапустить.
6. **Маржа у всех позиций получается ~8-10%**, это не баг: при закупке ≥300₽ цена продажи
   после наценки «Оптимум» почти всегда попадает в тир Ozon-комиссии 44% (цена ≥1500₽),
   что съедает большую часть плановой наценки.

## ВАЖНЫЕ ГРАБЛИ, ЭТАП 2 (фото)

7. **Prodnum ≠ Code.** У Микадо в прайсе ДВЕ разные колонки артикула:
   `Code` (то, что мы используем в итоговом Excel как "Код Mikado", например
   `of-4434g`) и `Prodnum` (внутренний идентификатор с брендовым префиксом,
   например `xzk-of-4434g` для Zekkert, `v500-...` для Mensan, `xcr-...` для
   CTR). **И сайт mikado-parts.ru, и уже собранная фототека на Yandex.Disk
   используют Prodnum**, не Code. Всегда строить карту `Code→Prodnum` из
   свежего прайса (колонки `Prodnum`/`Code`) прежде чем матчить/скрести.
8. **Кириллица в путях ломается при передаче через argv** — и в Bash, и в
   PowerShell (проверено на этом проекте). Ошибка выглядит как
   `FileNotFoundError` с мусорными байтами вместо кириллицы вместо реального
   "нет файла". **Решение: никогда не передавать кириллические пути как
   аргументы командной строки** (`--codes "...\без_фото.txt"` и т.п.) — вместо
   этого зашивать пути прямо в `.py`-файл как константы (`DEFAULT_*` в начале
   скрипта, необязательные `argparse`-флаги как оверрайд). Пути внутри
   `.py`-исходника (сохранённого как UTF-8) читаются нормально.
9. **Инструменты Bash/PowerShell по умолчанию песочат файловые операции** —
   изменения не видны ни в другом вызове того же инструмента, ни в реальной
   папке пользователя, пока не передан флаг **`dangerouslyDisableSandbox: true`**.
   Без него можно решить, что копирование/скачивание сработало (скрипт
   отчитается об успехе), а на самом деле реальный рабочий стол пользователя
   не изменится. **Для любой операции с файлами в рабочей папке транша
   (`Desktop\Озон-N\...`) — всегда `dangerouslyDisableSandbox: true`**,
   и финально проверять результат тем же флагом (лучше другим инструментом,
   например PowerShell, если писали через Bash).
10. **Фоновый запуск (`run_in_background: true`) вместе с `dangerouslyDisableSandbox`
    ненадёжен** — в этом проекте один фоновый запуск с отключённой песочницей
    привёл к тому, что уже записанные файлы (42 фото + без_фото.txt) исчезли
    после того, как последующий фоновый вызов упал с ошибкой. Возможно, откат
    относится к неудачному запуску целиком. **Для операций, пишущих в реальную
    рабочую папку — запускать в foreground**, даже если это долго (Selenium по
    134 артикулам ~30-40 мин) — бить на батчи по 10 минут (лимит foreground
    Bash-вызова), а не уходить в фон.

## ЧЕК-ЛИСТ ДЛЯ СЛЕДУЮЩЕГО ТРАНША (Озон-1000 и далее)

1. Уточнить у пользователя новый закупочный порог, если изменился (сейчас 300₽).
2. Проверить кэш `ozon_public_demand.json` — не протух ли (Ozon-цены/спрос могли
   измениться за месяцы) — при сомнении удалить старые записи и пересканировать.
3. Запустить оба скрипта (см. «Запуск» выше).
4. **Обязательно** проверить итоговое распределение по категориям и брендам на
   вырожденность (см. грабли #2) — если 2-3 категории/бренда съели >60% списка,
   разбираться в причине, а не сдавать как есть.
5. Явно спросить пользователя про фильтры-жидкости (масло/антифриз) и любые другие
   разовые исключения — они не сохраняются между траншами по умолчанию, только через
   явный код `is_excluded_liquid()`.
6. Свежий прайс Микадо — обязательно, не переиспользовать файл из прошлого транша.
